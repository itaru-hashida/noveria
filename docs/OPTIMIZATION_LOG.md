# Журнал оптимизаций: каждая гипотеза с флагом

**Действует с 10.11.2026.** Ветка `work`. Предыдущая история сессии — в
`docs/OPTIMIZATION_SESSION.md`; здесь с этого момента пишется **каждая**
проверенная гипотеза, удачная и неудачная, с флагом и замером.

Зачем отдельный документ: неудачные гипотезы терялись в переписке, и следующая
сессия проверяла их повторно. Здесь одна таблица отвечает на вопрос «это уже
пробовали?» без чтения истории целиком.

## Флаги

| флаг | значение |
|---|---|
| ✅ **ВНЕДРЕНО** | гипотеза подтвердилась замером, правка в ветке |
| ⚠️ **ВНЕДРЕНО, ШУМ** | правка оставлена как упрощение, но выигрыш в пределах разброса прогонов |
| ❌ **ОПРОВЕРГНУТО** | замерена и откачена: стало хуже или выигрыша нет |
| 🚫 **ОТКЛОНЕНО** | нельзя без изменения расчёта, RNG или порядка фаз |
| ⬜ **НЕ ПРОВЕРЕНО** | направление известно, замер не делался |

**Правило флага:** флаг ставится по замеру, а не по замыслу. Разница внутри
разброса прогонов (§5 `AGENTS.md`) — это ⚠️ или ❌, но не ✅.

## Записи с деталями

Каждая запись: гипотеза → чем проверялась → числа → вывод. Параметры прогона
указаны, иначе результат невоспроизводим.

### 22. Ценовая граница в `reachable_demand` и `investment_demand` — ✅

**Гипотеза:** `self.offers()` отдаёт предложения, отсортированные по
доставленной цене, значит после границы `price > order_price+EPS` или
`price >= landed-EPS` не остаётся ничего, что может покрыть заявку. Цикл
продолжал обход через `continue` и просматривал весь дорогой остаток.

**Чем проверялась:** `tmp/count_probe.py --seed 73129 --months 6 --warm 2`
(счётчики внутри цикла, до правки):

| счётчик | значение |
|---|---|
| предложений просмотрено в `reachable_demand` | 3 503 086 |
| из них за ценовой границей | 3 336 515 (**95,2%**) |
| хвост отброшен по цене / по нулевому объёму | 100% / 0% |
| предложений просмотрено в `investment_demand` | 1 285 929 |
| из них за ценовой границей | 1 000 083 (**77,8%**) |

Замер: `tmp/game_speed.py --seeds 73129,17,7,4231 --months 12 --warm 2`,
detail — дефолт движка (`none`), карта 40×30, полный `advance_turn`.
**0,993 → 0,891 s/ход**, отпечатки `--baseline tmp/base-new.json`:
**0 расхождений из 48**.

**Ловушка:** исключение собственного продавца нельзя ставить первым условием
`break` — собственное предложение может стоять в любом месте книги. Оно
проверяется отдельным `continue` уже после границы.

### 23. Предел ресурса на `(провинция, ресурс)` — ✅

**Гипотеза:** `investment_demand` для каждой ресурсной фирмы перебирал **все**
клетки мира, чтобы сложить `extraction_per_tile` по её провинции, хотя предел
зависит только от карты.

**Чем проверялась:** тот же счётчик: **564 000 просмотров клеток за 470
ресурсных вызовов** за 6 месяцев.

**Правка:** `self.resource_limits[(province, resource)]` считается один раз в
`EconomyServices._initialize_state`.

**Арифметика:** слагаемые собираются в списки и суммируются встроенным `sum`
в порядке `tiles.values()`. `+=` в аккумулятор даёт другой последний разряд:
`sum()` в Python 3.12 использует компенсированное сложение Неумайера. Повтор
ресурса внутри клетки убран `dict.fromkeys` — исходная проверка
`resource in tile['resources']` добавляла вклад один раз.

Замер: **0,891 → 0,862 s/ход**, отпечатки **0 расхождений из 48**.

### 24. Возврат инвестиций к интервалу — 🚫

**Гипотеза:** `investment_interval=3` почти не работает, потому что
`investment_dirty` взведён каждый месяц; если чинить — три месяца из четырёх
потеряют блок инвестиций (0,263 s/ход, 29,2% хода).

**Что выяснилось:** `record_market()` взводит флаг по платёжеспособному
дефициту в минимум двух месяцах истории. Проверено, что все 12 месяцев
подряд классифицируются как инвестиционные, то есть постоянный флаг может
отражать постоянный дефицит, а не ошибку разметки.

**Вывод:** пропуск обзоров меняет сроки строительства, резервы и потенциально
RNG. Экономия **недоступна при требовании побитового совпадения** и не
делалась.

### 17. «Кривая предложения» — ❌

**Гипотеза:** заменить перебор офферов в `quoted_cost` префиксными суммами и
бинарным поиском по объёму.

**Замер** (seed=73129, один ход, detail=none): 5 367 вызовов, промахов кэша
4 267, пройдено **3 931 оффер — менее одного на вызов**; покрыто объёмом
3 466 вызовов в среднем за **1,1 оффера**.

**Вывод:** цикл обрывается по `left <= EPS` почти сразу, кривая не нужна.
Ранний замер «69 офферов на вызов» был артефактом обёртки: счётчик считал
варианты, которые генератор `OfferView` пропускает после `break`.

### 18. Доставка один раз на площадку в `_market_book` — ❌

**Гипотеза:** `landed` зовётся на каждый оффер, хотя доставка зависит только
от площадки продавца (40,7 различных площадок на книгу).

**Замер:** вызовы `landed` 105 498 → 93 249, попадания в кэш те же.
Перемежающийся A/B из 4 пар: old 0,632 / 0,638 / 0,633 / 0,641 против
new 0,629 / 0,630 / 0,633 / 0,637; медианы **0,635 против 0,639 — хуже**.
Причина: `landed` и так попадал в кэш на 85%, а словарь `freights` добавлял
работу на каждой книге. Откачено.

### 20. numba / Cython / CUDA — ❌

**Гипотеза:** переписать горячие функции на компилируемый код.

**Замер:** 185 822 вызова за ход × 0,12 мкс = **0,022 с из 0,798 (3%)** —
это цена самих вызовов из Python, которую numba не убирает. Профиль плоский,
ни одна функция не превышает 6% времени.

**Вывод:** ускорять нечего на уровне языка; надо убирать работу. Согласуется
с §5 `AGENTS.md`: удаление дублирующих обходов дало 2,2× на чистом Python.

### 19. `numpy.sum` — ❌

**Замер:** расходится со встроенным `sum` в **63 случаях из 200** — массивы
меняют порядок суммирования, а значит траектория уходит. Неприменимо, пока
требуется побитовое совпадение.

### 29. Обновлённая разбивка хода — ✅ (инструмент)

**Гипотеза аудита:** прежняя разбивка недостоверна — `report['duration']`
заканчивается раньше commit и уведомлений, часть 3 получена как разность,
а обёртки `TurnService` могли не срабатывать.

**Чем проверялась:** `tmp/turn_split2.py --seed 73129 --months 12 --warm 2`,
внешний `time.perf_counter()` вокруг `advance_turn`, инклюзивное и
исключительное время по стеку вызовов.

**Числа (полный ход 0,865 s/ход):**

| часть | s/ход | доля |
|---|---|---|
| расчёт месяца (`step`) | 0,646 | 74,7% |
| сохранение | 0,077 | 8,9% |
| загрузка и подготовка | 0,059 | 6,8% |
| проверки вне step | 0,042 | 4,8% |
| commit, события, каркас транзакции | 0,041 | 4,8% |

Внутри `step` (доля от хода): планирование 16,8%, восстановление предприятий
13,8%, торги 10,0%, цены 5,9%, расчёты 5,9%, спрос 4,7%, план сырья 4,9%,
производство 3,1%, собственная работа вне этапов 3,2%.

**Две ошибки прежнего инструмента, найденные по замечаниям:**

1. обёртки `TurnService._integrity`/`_snapshot` ставились **после** создания
   сервиса, а фазы держат bound methods из `__init__` — обёртки не срабатывали,
   проверки показывались нулём;
2. момент входа в родительский этап перезаписывался моментом возобновления,
   поэтому инклюзивное время `step` схлопывалось в 0,001 s.

**Вывод:** `report['duration']` занижает ход на **0,018 s** — надо мерить
снаружи. Разбивка «до правок» (0,900 s: загрузка 0,062, инвестиции 0,263,
остальное 0,401, проверки 0,020, сохранение 0,155) **несопоставима** с новой:
там часть 3 была разностью, а инвестиции считались обёртками поверх `step`.

### 35. Числовое ядро `reachable_demand` на массивах + numba — ❌

**Гипотеза аудита:** стоимость участка — это представление данных и исполнение
циклов, а не число вызовов. Значит массивы + компилированный последовательный
цикл могут дать выигрыш, которого не дают настройки кэшей. Порядок операций
сохраняем буквально, без `fastmath` и перестановок.

**Среда:** numba 0.68.1 + llvmlite 0.50.0 пришлось ставить **обходом pip**:
`pip install` под песочницей падает на распаковке колеса
(`PermissionError` на `*.whl.metadata`, та же грабля `0o700`, что в §11
`AGENTS.md`, и она воспроизводится даже на `six`). Колесо скачано напрямую с
PyPI и поставлено из файла.

**Чем проверялась:** `tmp/numba_reachable2.py --seed 73129 --months 3 --warm 2`.
Три варианта на одном состоянии, побитовая сверка на каждом вызове:

| вариант | мкс/вызов | разложение |
|---|---|---|
| A. Python-цикл (эталон) | **59,8** | — |
| B. numba + полная сборка каждый вызов | 718,2 | подготовка 592,3 + ядро 125,8 |
| C. numba + переиспользование книг | 263,3 | подготовка 228,4 + ядро 35,0 |

**Ускорение участка: B 0,08×, C 0,23× — то есть в 4–12 раз МЕДЛЕННЕЕ.**

**Почему.** Python-цикл с `break` по ценовой границе трогает единицы
предложений: 35–60 мкс на весь расчёт по 69 группам. Ядро действительно
быстрое (35 мкс в C, и это уже с накладными numba), но **подготовка массивов
дороже самого расчёта в 4–10 раз**: нужно материализовать книги для 30 площадок
покупателей и 4 470 слотов, тогда как обход реально касается нескольких
десятков. Кэш книг дал 16 877 попаданий против 693 промахов и всё равно не
спас: остатки, участники, границы и слоты пересобираются на каждый вызов.

**Расхождения (B=107, C=305 из 743) — дефект моей пробы, не движка:** она не
воспроизвела точный порядок `OfferView` (фильтр неживых предложений, порядок
по `(цена, id)` при разных книгах, общий словарь остатков на все группы).
Эксперимент не внедрялся, поэтому расхождения на движок не влияют.

**Вывод:** гипотеза «основная стоимость — представление данных и циклы»
**опровергнута для этой функции**. Причина в форме расчёта: он короткий и
обрывается по цене, поэтому материализация стоит дороже, чем экономит.
Для переноса модуля на массивы нужен участок с длинными циклами по большим
массивам без обрыва — в `reachable_demand` такого нет.

**Что это НЕ доказывает:** что numba бесполезна вообще. Она полезна там, где
подготовка амортизируется по многим итерациям (например, полный проход
`settle` по всем счетам или `update_prices` по всем фирмам). Проверять надо
именно такие участки, а не короткие функции.

### 38. Узкий immutable-кэш доставки на один ход — ❌

### 39. Предагрегация `customer_demand_groups` + фильтр по цене — ✅

### 41. `distance` снимка через `path` вместо `landed` — ✅

Матрица расстояний в `agent_snapshot` брала длину маршрута из
`landed(tile, tile, good, 0)`, хотя нужны только расстояние и достижимость:
`landed` для этого умножал расстояние на вес товара и тариф и собирал кортеж
из четырёх полей на каждую пару. На 78 площадках это 6006 пар за сборку.

**Эквивалентность:** все 6006 пар совпали по расстоянию и достижимости; все 38
массивов и metadata идентичны (`np.array_equal`, сравнение ключей meta).

**Замер полного хода, inline (без пула)**, seed 73129, warmup 2, 12 месяцев,
один `advance_turn()` на месяц, траектории сторон совпали (сверялись по
сделкам, золоту и числу предприятий после каждого хода):

| | среднее | медиана | макс |
|---|---|---|---|
| `landed` | 834,6 мс | — | — |
| `path` | 815,6 мс | — | — |

12 пар ABBA (два прогона по 6): средняя разница **−12,7 мс (−1,5%)**, 95%
интервал `[−23,65; −1,75]`, медиана −10,8 мс, быстрее в **10 из 12**. Интервал
не накрывает ноль, поэтому правка оставлена.

**Почему с пулом выигрыш не виден.** `AgentTurn` подаёт пачки в пул и читает
результаты по готовности (`add_done_callback` + очередь), поэтому порядок
интентов зависит от расписания. Два прогона с пулом расходятся траекториями:

траектории дают дельты крупнее самой оптимизации, поэтому профиль с пулом
годится для долей, но не для решения «быстрее/медленнее».

**Вывод:** правка ускоряет игру в детерминированном режиме и не меняет расчёт.
С пулом она тоже ничего не замедляет, но её вклад меньше траекторного шума —
судить по нему нельзя.

### 42. Перепривязка книги к копиям заявок снимка — ❌

**Гипотеза.** `_planning_market_snapshot` создаёт новые dict заявок и новые
списки, поэтому ключ `(id(sell_list), площадка, товар)` промахивается 6740 раз
за 12 ходов. Но выводимая часть книги — порядок, landed-цены и котировки —
зависит только от `id`, `price` и `tile_id`, которые снимок не меняет. Значит
книгу можно не строить заново, а перепривязать: взять готовый план
`(landed-цена, id)` + `quotes` и подставить новые объекты заявок.

**Что проверено до правки (без изменений кода).** Пары «товар × площадка»
прослежены до и после снимка (`tmp/probe_book_snapshot_refs.py`,
`tmp/probe_book_inventory.py`):

| вопрос | ответ |
|---|---|
| поля записи книги | `source`, `options`, `quotes`, `board_id`, `first_live` |
| читается из заявки при использовании | `remaining`, `status`, `participant`, `province_id`, `quantity`, `id` |
| что книга копирует при постройке | landed-цена, порядок по `(цена, id)`, `quotes` |
| те же объекты заявок после снимка | **нет**: в `options` до снимка живые заявки (4260), после — копии (2480) |
| тот же порядок и landed-цены | **да**, во всех проверенных случаях |
| видимых строк через книгу до снимка | **0** (все заявки `expired`/`cancelled`), после — 91–92 |

**Проверка «переиспользовать как есть»** (`tmp/probe_reuse_book.py`): книга до
снимка, отданная после снимка, расходится с базой в 11 месяцах из 12
(сделки 962 → 979, выпуск хлеба 2496 → 2441 и т. д.). Причина — 2268 из 2708
переиспользований дают 0 видимых строк: живые заявки к этому моменту уже
отменены, а копии снимка ещё `active`. Переиспользовать объект книги нельзя.

**Правка.** План под парой (площадка, товар) + отпечаток `(id, price, tile_id)`
строится при постройке книги; на промахе ключа сверяется с новым списком и при
совпадении книга собирается из плана без `landed` и сортировки. Инвалидация:
`reset_report`, `invalidate_market_books`, `invalidate_routes`.

**Эквивалентность:** отпечатки совпали — seed 73129 12 мес (12/12), 36 мес
(36/36), seed 17 12 мес (12/12). Полный `pytest` — `340 passed, 6 skipped`
(с обходом окружения, см. ниже).

**Замер — и почему откачено.**

| стенд | база | правка | разница |
|---|---|---|---|
| полный ход, inline, 12 пар ABBA | 773,7 мс | 768,0 мс | −5,6 мс (−0,7%), интервал `[−14,3; +3,1]` |
| время внутри `_market_book`, 6 пар | 94,0 мс | 106,4 мс | **+12,4 мс (+13,2%)**, интервал `[−3,5; +28,3]` |

Интервал полного хода накрывает ноль, а измерение самого компонента
показывает рост: правка **медленнее**. Микробенчмарк объясняет причину
(`tmp/bench_rebind.py`): постройка 104,3 мкс, перепривязка 22,1 мкс, но
отпечаток 34,2 мкс платится на **всех** 6740 промахах, тогда как перепривязка
нужна лишь в 2480. Итог по 12 ходам отрицательный: 2480×(104,3−22,1) −
6740×34,2 ≈ **−26 мс**. Замена двух dict-ключей (отпечаток + `dict(quotes)`)
дороже, чем кажется: это уже третий случай в журнале (§38, «идеальный кэш
групп»), когда «бесплатная» проверка съедает выигрыш.

**Урок для следующей попытки.** Прежде чем строить план, нужен потолок,
который не меняет траекторию. Потолок «отдавать устаревшую книгу» для этого
негоден: он меняет расчёт и показывает −8,4% (правка выглядит выгодной).
Рабочий потолок — стоимость операций на тех же данных (`tmp/bench_rebind.py`).

### 43. Переиспользование книги, построенной до снимка — 🚫

Не «не проверено», а проверено и запрещено: живая книга держит ссылки на
заявки, которые `market_tail` отменяет. Копии снимка — другие объекты с
`status='active'`, поэтому через старую книгу планировщик видит 0 строк вместо
91–92. Расхождение траектории в 11 месяцах из 12. Менять ключ или убирать
копирование по-прежнему нельзя.

### Чем мерить A/B в этом репозитории
Последовательный A/B по одному процессу на сторону даёт систематический
перекос: BA-пары в среднем на 2% медленнее AB. A/A-контроль на том же стенде
показал +0,1%, то есть смещение не объясняет разницу целиком, но шумит.
Рабочий вариант — **обе стороны в одном процессе с чередованием ABBA**
(`tmp/ab_demand.py`): дрейф машины действует на обе стороны по очереди.
Дополнительно потолок считать обязательно: «идеальный кэш групп» оказался
**медленнее** на 5%, и без этой цифры правка выглядела бы как ошибка замера.

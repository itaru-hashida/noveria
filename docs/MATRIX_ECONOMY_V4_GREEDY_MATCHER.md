# V4 greedy matcher — эксперимент

Добавлен `shadow/v4_greedy_matcher.py`. Он не использует LP и dense matrix:

- получает предложения через существующий V3 `engine.offers`;
- тем самым повторно использует route-component индексы, landed cache и
  сортировку доступных sellers;
- обрабатывает buyers по `(limit desc, unmet_age desc, order_id)` только в
  рамках текущего прохода;
- применяет сделки через `commit_trade_atomic`.

ID не используется как межходовой приоритет: это только детерминированный
tie-break заявок с одинаковыми предыдущими ключами. В live V3 order schema
`unmet_age` отсутствует, поэтому там возраст равен нулю.

## Малый exact-контрпример

Два buyer и два seller, один товар:

- `high`: quantity 1, limit 10, budget 10;
- `low`: quantity 10, limit 5, budget 50;
- `cheap`: quantity 10, price 5;
- `dear`: quantity 1, price 10.

Greedy сначала отдаёт дешёвый товар `high`, затем `low`: объём **10**.
Exact LP отдаёт дорогой товар `high`, дешёвый `low`: объём **11**.
Это конкретно показывает, что быстрый matcher не является точным
максимизатором объёма.

Сумма стадий немного меньше total из-за внешнего orchestration overhead.

Это существенно быстрее прежних ~75 ms V3 matching-фазы, но сравнение по
объёму нельзя считать эквивалентным exact LP: контрпример выше доказывает
возможную потерю объёма. Наиболее безопасные варианты дальнейшей работы:

1. оставить greedy только как быстрый bounded/diagnostic режим;
2. добавить локальный fallback exact LP для конфликтных компонентов;
3. не включать greedy production-wide, пока не задано допустимое отклонение
   от exact allocation.

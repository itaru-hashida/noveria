# Handoff: параллельное планирование агентов

Ветка эксперимента: `experiment/parallel-agent-planning`, создана от
`work@0977539`. Цель — исследовать новую архитектуру расчёта предприятий:
параллельные agent-planning, асинхронная очередь намерений и long polling.
Не переписывать весь движок сразу и не смешивать эксперимент с текущим
`work`.

## Обязательный первый шаг

Перед реализацией задай владельцу проекта короткий список вопросов и дождись
ответов. Минимально нужно уточнить:

1. Допустима ли новая, недетерминированная траектория, если расчёты агентов
   детерминированы, но FIFO-порядок зависит от времени готовности потоков?
2. Должна ли заявка, готовая раньше остальных, исполняться сразу, или сначала
   закрывается фиксированное окно сбора намерений?
3. Какие типы агентов входят в первый эксперимент: только предприятия или также
   инвесторы и домохозяйства?
4. Какой ответ считается достаточным для первого прототипа: список заявок,
   частичное исполнение, причины отказа и состояние собственных запасов?
5. Какой минимум машинных ядер и какой целевой размер мира использовать для
   сравнения?

Не делай большие архитектурные предположения до этих ответов. Если ответа нет,
продолжай только с read-only прототипом и замерами.

## Зафиксированная идея

Публичный снимок начала хода → параллельные прогнозы агентов → FIFO-очередь
намерений → один последовательный исполнитель рынка → очередь результатов →
следующий этап производства.

```text
Snapshot(N)
    ↓
agent.plan(snapshot, own_state)
    ↓  (parallel workers / async completion)
IntentQueue (FIFO)
    ↓
MarketExecutor: reserve → execute → Outcome
    ↓
OutcomeQueue
    ↓
agent.observe(outcome)
    ↓
Snapshot(N+1)
```

Агент видит собственное состояние и публичный `MarketView`: цены, доступное
предложение, дефицит, доставку, труд и сырьё. Агент не видит внутренние планы,
счета и склады других агентов. Пекарня не знает мельницу; она подаёт заявку на
муку по доступности и цене рынка. Мельница отдельно подаёт заявку на зерно.

Производство новых товаров может поступать на следующий рынок. Не вводить
рекурсивный пересчёт «хлеб → мука → зерно → инструменты» до сходимости.
Цепочка должна проявляться через реальные заявки, клиринг, фактический выпуск и
результат следующего хода.

## Границы первого эксперимента

Сначала сделать 1–3 изолированных модуля или прототип без замены текущего
движка:

- `agent_snapshot.py` — компактный read-only снимок публичного рынка и личного
  состояния;
- `agent_planner.py` — расчёт намерения предприятия;
- `intent_queue.py` / `market_executor.py` — FIFO и последовательное
  резервирование/исполнение.

Не менять текущую V3 траекторию до shadow-сравнения. Первый прототип должен
уметь запускаться рядом с V3 на одном и том же сохранении и выдавать:
намерения, заявки, порядок FIFO, причины недоступности и предполагаемые
результаты. Исполнение в боевой V3 подключать только после отдельного решения.

## Параллелизм и асинхронность

Параллелить только чистый `plan()` на неизменяемом снимке. Общий ledger,
резервы денег и товаров, остатки заявок, сделки, производство и RNG не менять
из worker-ов.

`asyncio` нужен для orchestration и long polling, а не для ускорения CPU. Для
CPU-планирования сравнить последовательный вариант с постоянным пулом worker
процессов; Python threads считать только контрольным вариантом. Не создавать
процесс на каждого агента и не копировать полный мир каждому worker-у.

Long polling означает ожидание новых намерений с ограниченным окном:

```text
worker завершил план → enqueue(intent)
executor ждёт очередь до deadline или batch_limit
закрывает batch → FIFO-клиринг → Outcome
```

Чистый порядок готовности worker-ов делает траекторию зависимой от расписания.
Если это разрешено, зафиксировать как свойство новой версии. Если нужна
воспроизводимость, использовать отдельный seed/приоритет агента и каноническое
разрешение равенств; не полагаться только на timing ОС.

## Кэши и инкрементность

Ввести небольшие кэши внутри worker-а и снимка, без глубокой системы
инвалидации на первом этапе:

- `functools.lru_cache` для чистых расчётов по неизменяемым ключам;
- кэш маршрута/доставки по `(seller_tile, buyer_tile, good)`;
- кэш рецепта и числовых коэффициентов;
- кэш локального `MarketView` на batch/фазу.

Ключи не должны содержать изменяемые dict/list. Для кэшей, зависящих от
месячных заявок, использовать явную версию snapshot или batch. Не держать
неограниченные ссылки на объекты из прошлых ходов. Сначала ограниченные
`maxsize`, затем измерить hit/miss; не строить сложную инвалидацию до замера.

Инкрементность — минимальная: переиспользовать неизменяемые индексы и данные
снимка, пересчитывать только намерение конкретного агента при изменении его
входов. Не добавлять граф зависимостей производственных цепочек в первый
прототип. Рецепты можно представить как статический список/уровни для
порядка, но не запускать рекурсивную сходимость.

## Векторы и матричные расчёты

Проектировать горячие структуры как плотные/разреженные числовые массивы:

- numeric IDs вместо строк в горячих циклах;
- массивы цен, остатков, резервов, мощности, рецептур и координат;
- индексы `good × market`, `province × resource`, `agent → orders`;
- разреженные списки связей вместо плотной матрицы всех фирм × фирм;
- NumPy/Numba допустимы только там, где порядок операций и суммирование
  сохраняют нужную семантику. Не использовать `fastmath`, параллельные
  редукции или `numpy.sum` в точном режиме без проверки отпечатков.

Подготовка массивов входит в замер. Если упаковка dict-ов съедает выигрыш,
архитектура не считается успешной.

## Сравнение и критерии

Сначала сравнить архитектуру в shadow-режиме на одном снимке, затем полный
прогон. Обязательные параметры: `seed=73129,17,7,4231`, `months=12`,
`warmup=2`, `detail=none`, карта `40×30`; отдельно нужен увеличенный synthetic
world для проверки роста.

Мерить одинаково: полный `TurnService.finish`, включая load, step, save,
integrity, snapshot, commit и события; отдельно время планирования, передачу
снимка, очередь, клиринг и сбор результатов. Параллельный A/B запускать
парными процессами с одинаковым сидом и одинаковым числом workers; не делать
вывод по одной паре.

Для V3 сохранять отпечатки счетов, товаров, предприятий, сделок, причин заявок
и RNG. Новая агентная модель может иметь новую траекторию только после явного
решения о новой `RULES_VERSION`; тогда сравнивать инварианты: сохранение денег,
товарные балансы, резервы, отсутствие двойной продажи/покупки, причинность
дефицита, воспроизводимость при фиксированном seed/режиме.

Критерий технического успеха первого прототипа: корректный FIFO, отсутствие
гонок и двойного резервирования, bounded memory, измеримый выигрыш с учётом
overhead, и отсутствие деградации на малом мире. Не обещать 0,45 s/ход до
замера; цель архитектуры — рост стоимости по числу агентов и заявок, а не по
числу клеток и повторным глобальным обходам.

## Что не делать

- не давать агентам прямой доступ к чужим внутренним объектам;
- не исполнять ledger из worker-ов;
- не параллелить сделки с общими запасами без отдельного детерминированного
  протокола конфликтов;
- не использовать время завершения worker-а как скрытый приоритет без решения
  владельца;
- не переписывать весь `v3.py` до shadow-прототипа и замеров;
- не считать `asyncio` CPU-ускорением;
- не добавлять рекурсивную сходимость производственных цепочек.

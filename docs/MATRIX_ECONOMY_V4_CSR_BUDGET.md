# V4 CSR: бюджетное ограничение и ограниченный эксперимент

Эксперимент выполнен на одном готовом snapshot seed `73129`. Мир и V3 не
изменялись; полный pytest не запускался. Скрипт:
`scripts/experiment_v4_csr_budget.py`.

## Разделение случаев

Обычный bipartite max-flow корректен по физическому объёму, если для каждого
покупателя бюджет не связывает выбор рёбер: бюджет покрывает весь допустимый
спрос по максимальной delivered price. Также бюджет можно свернуть в capacity
источника, если все допустимые рёбра покупателя имеют одинаковую цену:
`capacity = min(quantity, budget / price)`.

Если у покупателя есть разные delivered prices и бюджет активен, это уже
ограничение стоимости. CSR хранит граф эффективно, но само по себе не делает
такой граф обычной сетевой задачей: нужен cost/budget-aware solver или
специализированное перераспределение.

## Результаты

| Вариант | Время решения | Объём | Потеря к exact | Бюджет | Приоритеты |
|---|---:|---:|---:|---:|---:|
| Старый Repair из `10a323e` | 2.26 ms | 3433.570491 | 0.835150 | 0 | не exact |
| Текущий BFS Repair | 38.02 ms | 3434.405641 | 0 | 0 | 22 buyer изменены, 20 нарушений относительно LP |
| CSR max-flow, scale `1e6` | 3.55 ms | 3434.405642 | менее `1e-6` | 0 с допуском `2e-6` | 244 buyer изменены, 44 нарушения |
| Exact lexicographic LP | 90 368.32 ms | 3434.405641 | 0 | 0 | эталон |

При строгом пороге `1e-7` прежние 8 покупателей отмечались как нарушившие
бюджет, но это только ошибка целочисленного масштабирования: максимальное
превышение `1.6799e-6`, сумма превышений `7.5805e-6`. Это не основание для
простого обрезания покупок. На масштабе `1e9` SciPy max-flow дал некорректно
заниженный поток из-за ограничений целочисленной реализации и исключён из
сравнения.

## Полная торговая фаза

На том же snapshot для текущего BFS Repair:

|---|---:|
| Решение | 38.02 ms |
| Применение результата | 27.63 ms |
| Snapshot + решение + применение | 467.86 ms |

Включение snapshot показывает стоимость полного shadow-пути; создание мира в
число не входит.

## Почему старый Repair потерял 0.835

Исторические `6.26 ms` относились к другой версии Repair — BFS с поиском путей,
зафиксированной позднее в `bfbaf7a`. В текущем сравнении `old_repair` намеренно
воспроизводит старую реализацию из `10a323e`, поэтому `0.835150` — не регрессия
версии 6.26 ms, а сравнение разных исторических алгоритмов. Текущий BFS
возвращает exact объём, но не lexicographic priority и существенно дороже.

## Вывод

CSR max-flow — дешёвый кандидат для компонент с неактивными или сводимыми к
capacity бюджетами. На этом snapshot он сохраняет объём и не имеет реального
денежного нарушения после учёта квантования, но не гарантирует LP-приоритеты.
Для активных разных цен и бюджетов обычный max-flow применять нельзя. Текущий
Repair также не является математически точным. Интеграция в runtime не
выполнялась.

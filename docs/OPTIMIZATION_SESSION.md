## Отрицательный результат: матрица расстояний

Была построена числовыми ID площадок и плотной матрицей на месяц, чтобы
`landed` читал расстояние по индексам вместо словарного ключа из строк.
**Стало медленнее:** 0,804 → 0,854 s/ход, `project_requests` 2,71 → 3,47 с.
Откачено, в историю не вошло.

Причина: `path()` уже отдаёт дерево Дейкстры из кэша, и словарный доступ
дешевле, чем `transport_matrix()` + два поиска по индексам. Замена способа
добычи величины не помогает, если добыча не была дорогой.

**Правило, которое из этого следует:** сначала выясни, что именно стоит
времени, и только потом меняй форму. В этом случае дорогим был сам факт
1,1 млн вызовов, а не вычисление внутри них.

## Уточнение оценки второго прохода (после сессии)

Замер по фазам (seed=73129, months=4, detail=none, сумма времени фаз):
`production_outlook` в финансировании **0,78 с**, в планировании **0,30 с**

`project_requests` при `investment_interval=3` идёт **каждый месяц**: 8
адресных обзоров против 4 полных за 12 месяцев. Адресный обзор дороже полного
по числу вызовов, потому что `allowed_goods` фильтрует уже внутри цикла
инвесторов, а внешний обход не сокращается. `investment_demand` попадает в
кэш на 66%.

## Правка: пострыночная история продаж

`settle` считал неиспользуемую переменную `sold` (полный обход сделок на
каждое предприятие), а затем строил `sales_history` и `stock_sales_history`
вложенными обходами: **1,7 млн итераций за ход** (1550 слотов склада × 853
сделки плюс 230 фирм × 1577 заявок). На профиле это `v3.py:3415`, 0,594 с
собственного времени — второй по величине участок после `dict.get`.

Заменено одним проходом по заявкам и сделкам с группировкой по
`(продавец, товар)`. Важная деталь: в Python 3.12 `sum()` суммирует float с
компенсацией погрешности (Neumaier), поэтому накопление в словаре дало
расхождение в последнем знаке у 22–35 счетов за месяц. Слагаемые собираются
в списки и складываются тем же встроенным `sum` — история продаж совпала
побайтово (1803 записи, 0 расхождений).

Замер: **0,760 → 0,651 s/ход**, −14,3%. Отпечатки состояния на матрице
4 сида × 12 месяцев — **0 расхождений из 48**.

## Правка: ключ кэша `landed` из трёх полей

109 498 вызовов `landed` за ход строили ключ из пяти полей
`(продавец, покупатель, товар, вес, тариф)`, доставая вес и тариф из двух
словарей на каждый вызов. Вес товара и тариф перевозки — авторские константы
контента: игра их не меняет, ни один тест не переписывает. Ключ стал
`(продавец, покупатель, товар)`, пара `(вес, тариф)` запоминается по товару.

**Важно:** произведение НЕ предвычисляется. Было `distance*weight*rate`
(слева направо), `distance*(weight*rate)` отличается в последнем бите и
разводит траекторию с первого месяца — проверено, отпечатки расходятся.

Замер: 0,640 → **0,636 s/ход**. Попаданий в кэш 85,8% (90 549 из 105 498),
отпечатки — 0 расхождений из 48.

| ключ `customer_demand_groups` без цены предложения (группы хранят заявки, `_solvent_volume` считает на месте) | ключ стал общим, но попаданий прибавилось мало, а сумма платёжеспособности теперь считается на каждый вызов: **0,639 → 0,679 s/ход**, стало хуже |
| кэш `net_price` по ревизиям | попаданий всего 34%, риск не оправдан |
| адресная версия рынка в ключах `quoted_cost` / `reference_price` | попадания 21,5% → 27,3%, в пределах шума |
| адресная версия в ключе `customer_demand_groups` | 1947 → 1847 различных ключей, не стоит усложнения |

**Урок про точность float.** При переписывании `_solvent_volume` нашлась
ловушка: `reserved*(1/landed)` вместо `reserved/landed` различается в
последнем бите и разводит траекторию с первого месяца (отпечатки разошлись
48 из 48). Проверка «сравни старую и новую формулу на одном состоянии» ловит
это за один прогон, а матрица сидов — только после.

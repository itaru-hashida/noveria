# CSR и обычный max-flow для V4

Профиль запускается командой python -B scripts/experiment_v4_csr.py. Все
решатели получают один snapshot seed 73129. Время подготовки snapshot и
применения сделок исключено.

| Алгоритм | Время | Объём | Потеря к exact | Денежные нарушения |
|---|---:|---:|---:|---:|
| Старый Repair | 2.26 ms | 3433.570491 | 0.835150 | 0 |
| BFS Repair | 34.77 ms | 3434.405641 | 0 | 0 |
| CSR max-flow | 2.88 ms | 3434.405642 | менее 1e-6 из-за масштаба | 8 |
| Exact LP | 77828.36 ms | 3434.405641 | 0 | 0 |

Исторический замер старого Repair был 6.26 ms. Повтор на текущем snapshot
дал 2.26 ms. Это значение использовано в таблице как same-snapshot baseline.

Допустимый граф имеет форму CSR `910 x 616`, `1669` рёбер и `13352` bytes
данных. Max-flow использует целочисленное масштабирование quantities с
коэффициентом 1e6. Он гарантирует максимальный физический объём, когда
денежные ограничения неактивны. Такой случай включает budgets, которые
заранее можно свернуть в source capacity, например при одной постоянной
цене для каждого покупателя.

Разные delivered prices на рёбрах одного покупателя делают budget
ограничением стоимости, а не только количества. Обычный max-flow этого не
видит. На live snapshot он достиг объёма exact, но создал 8 покупателей с
превышением бюджета. CSR-представление не устраняет это ограничение.

В прототипе сохранена отдельная векторная проверка рёбер и sparse max-flow.
Пакетное физическое перераспределение можно использовать для верхней границы
объёма, но оно не подключается к runtime и не заменяет admissible allocation.
Матричный BFS Repair сохранён отдельным экспериментом. Его дальнейшее
развитие остановлено.

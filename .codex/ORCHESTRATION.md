# Регламент оркестрации агентов

## Роль root-агента

Root-агент выступает как архитектор, тимлид и ревьюер. Он:

- определяет архитектурную цель и границы задачи;
- разбивает работу на маленькие независимые срезы;
- выдаёт агенту только необходимый контекст;
- запрещает чтение нерелевантных файлов;
- принимает или отклоняет результат по diff, тестам и benchmark;
- не считает задачу завершённой без commit и проверки.

## Ограничение контекста агента

Каждое поручение обязано содержать:

1. цель одного среза;
2. разрешённые файлы и каталоги;
3. файлы, которые запрещено читать или менять;
4. точный API/контракт;
5. тесты и критерии готовности.

Агенту запрещено делать общий обзор репозитория, искать «лучшую архитектуру» во
всём проекте или открывать большие нерелевантные файлы. Если для работы нужен
дополнительный файл, агент сначала задаёт один конкретный вопрос root-агенту с
объяснением, какой символ или контракт ему нужен. Нельзя запрашивать «весь
проект» или читать файлы ради общего понимания.

## Шаблон поручения

```text
Задача: <один конкретный результат>

Разрешённые файлы:
- <file A>
- <file B>
- <new test file>

Не читать и не менять:
- <unrelated directories/files>

Контракт:
- <API, ownership, ordering, invariants>

Ограничения:
- не менять поведение вне среза;
- не делать рефакторинг соседних модулей;
- не добавлять новые зависимости без согласования.

Проверки:
- <focused test command>
- <exact/benchmark command>
- git diff --check

Результат:
- commit;
- список изменённых файлов;
- краткий diff;
- тесты и benchmark;
- известные ограничения.
```

## Commit и ревью

Агент обязан сделать отдельный commit. Root-агент после ответа агента проверяет:

```text
git show --stat --oneline <commit>
git diff <parent>..<commit> --check
git diff <parent>..<commit> -- <разрешённые файлы>
git status --short
```

Root-агент дополнительно запускает минимальные тесты и проверяет, что diff не
затронул запрещённые файлы. Агентский commit не считается принятым до этой
проверки.

## Вопросы и эскалация

Агент может задать вопрос только если без него нельзя сохранить контракт или
exact-семантику. Вопрос должен быть коротким и содержать:

- конкретный блокирующий символ/решение;
- две возможные трактовки;
- предложенный безопасный вариант.

Не задавать вопросы о стиле, очевидных локальных деталях или общей архитектуре.
Если есть безопасное решение в рамках контракта, агент принимает его сам и
фиксирует допущение в отчёте.

## Параллельная работа

- Не давать двум агентам менять один файл одновременно.
- Каждый срез должен иметь отдельный worktree/ветку, если существует риск
  пересечения.
- Исследование без правок и реализация — разные поручения.
- После интеграции одного среза следующий агент получает новый commit как базу.

## Приоритет качества

Порядок проверки:

1. diff scope;
2. сборка/синтаксис;
3. focused tests;
4. exact replay и RNG;
5. benchmark cold/warm;
6. только затем следующий срез.

Если benchmark не дал измеримого выигрыша или тесты требуют обхода контракта,
изменения не принимать и не наращивать поверх них следующий этап.
